# Ticket 20 R2 D4: diagnostics outside the authority boundary

Status: D4 production CLEARED after independent review of 945ea482 reds. Implementation is in progress; production acceptance, regression and performance gates remain pending. The original reds remain in TICKET-20-D4-REDS.md. R2 as a whole is NOT accepted. R3, operator routes, capacity, activation and push remain held.

## Why the boundary changes

The one fresh D1/D2 production gate at product/tool pin 7fe71f7 failed. Heavy writes had median 0.228606800 s and maximum hold/peer 0.386682400/0.386908700 s; samples 8 and 9 missed 0.270 s and only one of ten met the 0.216 s margin. Structural reads also missed, at 0.270486300/0.271032500 s in sample 8. Summary and both import selections passed. Every replace-retry counter was zero. These are NORMAL misses, with no excluded samples or replacement run. [All 50 samples and phase summaries](../history/TICKET-20-DIAGNOSTICS-D1-D2-GATE.md) are retained separately from the original failed gate and instrumented profile.

The reviewer selected D4 instead of D3 evidence reuse: diagnostic disk/validation/inventory work leaves the engine and catalog boundary. Neither the 0.270 s hard limit nor retained-state budgets change. No claim about the cause of an individual historical outlier follows from the correlation between the two sample-8 misses.

## Ownership and phases

Each affected public service call is an orchestrator that starts without a caller-held engine/catalog boundary. Healthy paths needing no diagnostic keep their existing guarded behavior. A diagnostic branch has these phases:

|Phase|Locks and work|Permitted effects|
|---|---|---|
|A, capture|Engine + catalog boundary, existing authoring reads and authority checks; a memory-only attachment snapshot under the authoring RLock|Existing activation to ACTIVE may already have happened. Capture a detached immutable intent and continuation. No diagnostic owner lock, diagnostic read/write, new terminal transition, result disposition or diagnostic-dependent ACK.|
|B, persist|Outside engine/catalog and authoring locks. Diagnostic RLock + existing diagnostic process lock + body process lock|Full graph validation, encoded-cap checks, inventory, body put, metadata fsync/replace and durable receipt, exactly through the current diagnostic owner. No authority callback or boundary entry.|
|C, settle|Re-enter engine + catalog boundary, re-read current request/claim/authority and the retained result when relevant|Only after a durable receipt and successful revalidation, finish the captured continuation. No diagnostic owner read, lock, report or write.|

Release all A locks before B, and release all B locks before entering C. A failure in B returns the existing typed diagnostic unavailability, with no C effect or fabricated diagnostic id. A durable B followed by C refusal leaves a genuine retained diagnostic and no stale state transition. Diagnostics are evidence of an observation, never authority to admit a version, cancel a request or repair an ACK.

No lock-release trick on an outer RLock is allowed. In particular, releasing a service's nested `with` while its caller still owns the boundary does not implement this contract. Before A, the driver checks channels.engine._lock._is_owned(), channels.catalog._lock._is_owned() and store._lock._is_owned(). These are current-thread CPython RLock ownership queries; _is_owned is used in tests today (test_artifact_coordination.py), and this would be its FIRST production use. If any query is unavailable/non-callable, raises, returns an indeterminate result or reports current-thread ownership, raise private _ArtifactBoundaryHeld(ArtifactUnavailable), fixed internal code artifact_boundary_held and text "Artifact diagnostic operation requires an independent authority boundary.", no diagnostic or state effects. It maps to existing 503 artifact_storage_unavailable with no private text leak. The driver also checks all three ownership predicates immediately before B; a regression there fails closed rather than persisting inside a caller lock. Add test_diagnostic_driver_refuses_caller_held_boundary as an observed behavioral red after clearance.

## Attachment and legacy-marker lock edge

The store gains `_capture_diagnostic_attachment(request_id, dispatch_id)` returning the same Hex32-or-null first-attachment decision from cached memory under the authoring RLock only. It checks cached authoring held/known/legacy state, performs no file IO and never takes the diagnostic RLock. Non-null held authoring raises ArtifactUnavailable with the existing authoring text. A null diagnostic key needs no healthy authoring owner, except for the sticky legacy rule. Imported requests do not attach. Both this new capture method and existing _snapshot_diagnostic_attachment share one pure cached attachment implementation; the facade keeps its outside-boundary diagnostic propagation, while service capture reads the marker without taking the diagnostic lock. No duplicated attachment predicate.

The current facade snapshot calls `_set_legacy_hold`, which takes the diagnostic RLock. Service capture must not use that edge. A private shared `threading.Event`, `_diagnostic_legacy_marker`, conveys only the sticky development-v1 hold between the two owners. Create it before the authoring constructor calls _load_index, since load can set the marker before the diagnostic owner exists; set it at the SINGLE legacy-recognition assignment in _load_index (merged artifact_store.py:918). The constructor and _check_index at artifact_store.py:925-941 reach that INLINE recognition branch. _persist does not directly call _load_index: it invokes _check_index and honors the sticky flag. There is no recognition helper or separate persistence set-site; do not invent three marker setters. Setting the event never takes the diagnostic lock. Both owners remain sticky until a fresh owner after explicit offline repair, as already frozen.

The proposed diagnostic constructor becomes `ArtifactDiagnosticStore(data_dir, *, hold_unreadable=False, legacy_held=False, _legacy_marker=None)`. The optional private marker is an Event or null; standalone owners create their own marker, and legacy_held=True sets it. ArtifactStore passes its shared marker. All report/error sites, including the facade reads currently at artifact_store.py:1764/1796, derive legacy-held from that marker as well as the existing local flag, so capture need not synchronize it by acquiring the diagnostic lock. This is a private in-memory coordination change, not a schema field or a data migration.

The diagnostic owner tests that marker at transaction entry and before and after metadata publication. It does not test the marker again between candidate encoding and the body put. Its existing legacy-held error/report takes precedence. A marker observed before B refuses B without creating diagnostics.json or copying old diagnostic rows. A legacy change discovered concurrently with an already executing filesystem replace is a cross-file fault seam, not a rollback transaction: preserve any landed bytes, mark the diagnostic owner held, refuse C, and never reset/merge the old index. Add an Event test for this seam; do not claim atomicity across the two files. The ordinary standalone facade remains usable outside a boundary and preserves its R2 typed projections.

## C guard and changed-state outcomes

For live_claim, reservation_resume and retained_recovery work, C rechecks the applicable capability, identity/binding, active current channel and mode-specific queue predicates, plus exact audit and request state/reason/version/channel. Private brief ownership is captured/rechecked for live_claim and retained_recovery, but not reservation_resume. Reservation resume can fail its source packet before any brief exists; its authority is the captured request/audit, producer and queue projection. No extra private-brief read is introduced in A or C for that mode. fulfilled_replay, fulfilled_ack and terminal_saved do NOT acquire a new active-channel requirement. For retained recovery, keep the existing sealed-result/managed-launch and recovery-proof rules; do not add a live-worker requirement to fulfilled lost-ACK repair. Parent/source/content snapshots are immutable, but request state and authority are re-read. A recorded bad-packet observation need not be re-read from disk in C; repairing that file during B does not erase the diagnostic or change the historical failure branch.

## Reads and lock order

Source search at 7fe71f7 found no production caller of `ArtifactStore.diagnostics()` or `request_diagnostics()` outside their store definitions/delegation. The earlier structural timing harness deliberately invoked the report inside a shared boundary; that is a harness scope, not a hidden production call site. D4 replaces it with an outside-boundary report plus a real concurrent peer boundary user. Future reader/operator packages must call these report methods outside the boundary too.

`diagnostics()` copies authoring references/object-error observations under the authoring RLock, then moves the directory globs/resolve/stat orphan inventory OUTSIDE that lock. The report is a detached observational snapshot, not a transactionally current inventory; references added after capture can make an observation stale, and no state/authority decision may consume it. Diagnostic report IO also runs after releasing authoring. Keep safety guards and existing error projection. A file removed between outside-lock enumeration and stat raises OSError, and this report call marks owners.authoring unavailable with the fixed authoring_unavailable error, null aggregate count and partial/truncated true under the current catch. It does NOT latch _held or poison a later healthy authoring operation/report. As today, an error drops ALL authoring observations from this report call, not a partially accumulated authoring subset; independently healthy diagnostic rows remain available. This transient classification is an explicit consequence of the observational scan; do not silently swallow it as a successful empty inventory. `request_diagnostics()` is ledger-only. Neither method may enter engine/catalog or hold authoring while taking the diagnostic owner lock. Slow diagnostic reads, validation, body inventory and fsync must not delay a peer cancel/Stop through any shared engine/catalog or authoring lock. This does not promise that unrelated authoring-index disk work is lock-free.

Allowed edges: engine -> catalog -> authoring for A/C, then all released; diagnostic -> diagnostic process -> body process for B. No engine -> diagnostic lock edge in capture, no diagnostic -> authoring or diagnostic -> engine edge. The nonblocking legacy event communicates a hold, never authority. No invocation-local intent, receipt or callback is stored on either owner or reused by another thread/call.

## Crash windows, idempotence and settlement faults

|Crash/failure point|Durable state and retry/recovery|
|---|---|
|After A, before B|Only pre-existing effects such as activation remain. No diagnostic-dependent terminal change or ACK. Same worker input can retry; cancel/Stop remain available. Startup follows the current live/transport/outbox rules, never infers an intent from memory.|
|Body put before metadata commit|Existing possible orphan body counts toward quota; no diagnostic receipt or C. Preserve current body-failure versus uncertain-metadata-commit rules.|
|B durable, before C|Diagnostic is retained, request may still be live. Retry reconstructs and revalidates the intent from trusted inputs, and deterministic detail ids deduplicate. A different intervening overflow key can increment the bounded summary again under the existing latest-key-only rule; this is not an exactly-once counter claim. No new journal or overflow-id history.|
|C terminal change saved, before fence|Existing partial state/fence window remains. No rollback or second version. Transport error is reported/held under existing rules, and Stop/cancel transport reconciliation stays independent of diagnostics. Do not invent automatic terminal-request resume or a new repair state machine.|
|C outbox disposition saved, before caller result|Replay sees disposition and uses current retained-result policy; it cannot admit that result. Durable diagnostic id is genuine.|

For sealed saved results, startup/resume/lost-ACK recovery can reconstruct the operation from the existing private brief, seal, outbox and committed version checks. A fulfilled row with matching content still repairs its lost ACK, without changing imported or fulfilled rows. For rejected raw API output, validation intentionally runs before `box.save` (R1); there may be no durable raw result after B. Startup must not infer a terminal invalid_response transition from diagnostic contents. The request remains live until an authenticated retry, cancel/Stop, or existing terminal-empty-transport settlement. This is an explicitly retained diagnostic-first crash window, not a new recovery authority.

B's process-lock timeouts remain 10 s + 10 s, plus unbounded OS IO/scheduling residual. FAULT writes return typed diagnostics unavailability and no C effect; already durable earlier effects remain. B has no hard wall-clock latency claim. C's authoring/fence/disposition failures keep their current fault classifications, with no success response manufactured after uncertainty.
